可以，我们接着把这套 baseline 管线讲清楚。你现在可以先把它理解成一条流水线：

```text
配置文件
  -> 实验入口 run_baseline.py
  -> 读取 TableShift 四个 split
  -> 训练集拟合预处理器
  -> 所有 split 转成模型能吃的数组
  -> 构造 MLP

```

**1. 项目结构**
你的核心代码现在在 [src](C:/Users/zanyan/Desktop/AMLas/src) 里：

```text
src/
  configs/       实验配置
  data/          数据读取和预处理
  models/        模型结构，比如 MLP
  training/      训练循环、评估、指标
  methods/       方法封装，目前 ERM
  experiments/   实验入口脚本
  utils/         随机种子、读写文件等工具
```

这正是之前那段 AI 建议的“实验管线”风格。它不是一个巨大的脚本，而是把每个职责拆开。以后你想改模型，就看 `models/`；想改指标，就看 `training/metrics.py`；想加 TTA，就放到 `methods/tta/`。

**2. 配置文件在控制实验参数**
主配置是 [default.json](C:/Users/zanyan/Desktop/AMLas/src/configs/default.json)。它决定：

```json
{
  "datasets": ["assistments", "..."],
  "model": {
    "hidden_dims": [256, 128],
    "dropout": 0.1
  },
  "training": {
    "epochs": 50,
    "batch_size": 512,
    "lr": 0.001,
    "weight_decay": 0.0001,
    "patience": 8
  },
  "seeds": [0, 1, 2]
}
```

你可以把它理解成“实验菜单”。代码不应该到处写死学习率、epoch、batch size，而是从这里读。这样以后你做消融实验时，改配置比改代码安全得多。

另外 [datasets.json](C:/Users/zanyan/Desktop/AMLas/src/configs/datasets.json) 记录了每个数据集的 target 名，比如 `assistments` 的 target 是 `correct`。但当前入口脚本其实没有使用这个文件，因为 TableShift 已经把 `X` 和 `y` 分开存成 CSV 了，所以 target 列不用从原表里切出来。它现在更像一个后续扩展点。

**3. 实验入口是 run_baseline.py**
真正启动实验的是 [run_baseline.py](C:/Users/zanyan/Desktop/AMLas/src/experiments/run_baseline.py:38)。

它做的事情可以拆成三层：

第一层：解析命令行参数。

比如 README 里给的命令：

```powershell
conda run -n aml python src\experiments\run_baseline.py --dataset assistments --seeds 0 --epochs 3
```

意思是：只跑 `assistments`，只用 seed 0，只训练 3 个 epoch。

第二层：决定这次实验跑哪些数据集、哪些 seed、用 CPU 还是 GPU。这部分在 [resolve_datasets](C:/Users/zanyan/Desktop/AMLas/src/experiments/run_baseline.py:89) 和 [resolve_device](C:/Users/zanyan/Desktop/AMLas/src/experiments/run_baseline.py:97)。

第三层：对每个 `dataset + seed` 调用 [run_one_dataset_seed](C:/Users/zanyan/Desktop/AMLas/src/experiments/run_baseline.py:103)。这是最核心的单次实验函数。

**4. 单次实验的核心流程**
[run_one_dataset_seed](C:/Users/zanyan/Desktop/AMLas/src/experiments/run_baseline.py:103) 基本就是 baseline 的主线：

```text
set_seed(seed)
load_tableshift_dataset(...)
prepare_tableshift_arrays(...)
make_loader(...)
model = MLP(...)
train_erm(...)
evaluate_binary_classifier(...)
return result row
```

逐步说：

`set_seed(seed)` 固定随机性。它在 [seed.py](C:/Users/zanyan/Desktop/AMLas/src/utils/seed.py:7) 里设置 Python、NumPy、PyTorch 的随机种子。这样同一个 seed 的结果尽量可复现。

`load_tableshift_dataset(...)` 读取 CSV。代码在 [tableshift_loader.py](C:/Users/zanyan/Desktop/AMLas/src/data/tableshift_loader.py:50)。

它会读四组 split：

```text
train     Xtrain / ytrain
val       Xval / yval
id_test   Xidtest / yidtest
ood_test  Xood / yood
```

这四个 split 非常重要：

```text
train: 用来训练模型参数
val: 用来 early stopping 和选择最佳模型
id_test: 同分布测试集，用来衡量普通泛化
ood_test: 分布外测试集，用来衡量 distribution shift 下的性能
```

实验纪律上，`ood_test` 的 label 只能最终评估用，不能参与训练、调参、早停。

**5. 预处理只在训练集上 fit**
预处理代码在 [preprocessing.py](C:/Users/zanyan/Desktop/AMLas/src/data/preprocessing.py:24)。

这里的关键类是 `TabularPreprocessor`：

```text
fit(train.X)
transform(train.X)
transform(val.X)
transform(id_test.X)
transform(ood_test.X)
```

这点很关键：预处理器只在训练集上 `fit`，然后应用到 val、ID、OOD。这样不会把测试集分布的信息泄漏进训练过程。

当前预处理做了三件事：

```text
1. 把所有列转成 numeric
2. 无法转成数字的值变成 NaN
3. 用训练集 median 填缺失值
4. 用训练集均值/方差做标准化
```

这是一版很基础的 tabular baseline。它的优点是简单、稳定、能跑；缺点是如果某些数据集有真正的类别特征，当前代码没有 one-hot encoding，而是强行转 numeric。后面如果 baseline 要更严谨，`preprocessing.py` 是一个很值得升级的地方。

**6. MLP 模型**
模型定义在 [mlp.py](C:/Users/zanyan/Desktop/AMLas/src/models/mlp.py:5)。

结构大概是：

```text
input features
  -> Linear
  -> BatchNorm
  -> ReLU
  -> Dropout
  -> Linear
  -> BatchNorm
  -> ReLU
  -> Dropout
  -> Linear 输出 1 个 logit
```

最后输出的是一个 `logit`，不是概率。二分类里常见流程是：

```text
logit -> sigmoid -> probability -> threshold 0.5 -> 预测类别 0/1
```

所以训练时用的是 `BCEWithLogitsLoss`，它内部会更稳定地处理 sigmoid + binary cross entropy。

**7. ERM 训练逻辑**
训练函数在 [trainer.py](C:/Users/zanyan/Desktop/AMLas/src/training/trainer.py:50)。

ERM 是 Empirical Risk Minimization，你可以先把它理解成“普通监督学习 baseline”：

```text
只用 train features + train labels
最小化 BCE loss
不做测试时适配
不使用 OOD label
```

训练循环里每个 epoch 都做：

```text
model.train()
遍历 train_loader:
  前向传播 logits = model(X)
  计算 loss
  loss.backward()
  optimizer.step()

然后在 val_loader 上评估
如果 val balanced accuracy 变好，就保存当前模型
如果连续 patience 次没变好，就 early stop
最后恢复 best_state
```

这里有两个细节值得注意：

`pos_weight`：代码在 [trainer.py](C:/Users/zanyan/Desktop/AMLas/src/training/trainer.py:112)。如果正负样本不平衡，它会给正类更高权重。很多医学、教育、社会数据都是类别不平衡的，所以这个设置有意义。

`best_state`：代码会保存验证集表现最好的模型参数，而不是默认用最后一个 epoch 的模型。这就是 early stopping 的核心。

**8. 评估指标**
评估代码分两层：

[predict_probabilities](C:/Users/zanyan/Desktop/AMLas/src/training/evaluator.py:9) 做模型预测，把 logits 经过 sigmoid 变成概率。

[compute_binary_metrics](C:/Users/zanyan/Desktop/AMLas/src/training/metrics.py:21) 把概率按 threshold 变成 0/1 预测，然后算：

```text
Accuracy
Balanced Accuracy
F1
```

这三个指标里，你尤其要关注 `balanced_accuracy`。普通 accuracy 在类别不平衡时可能很骗人，比如 95% 都是负类，模型全预测负类也能有 95% accuracy。Balanced accuracy 会分别看正类、负类的识别能力，再平均，更适合这种 baseline 对比。

**9. Generalization Gap 是什么**
在 [run_baseline.py](C:/Users/zanyan/Desktop/AMLas/src/experiments/run_baseline.py:165) 返回结果时，代码计算了：

```text
generalization_gap_accuracy = id_accuracy - ood_accuracy
generalization_gap_balanced_accuracy = id_balanced_accuracy - ood_balanced_accuracy
generalization_gap_f1 = id_f1 - ood_f1
```

你可以理解成：

```text
模型在正常测试集表现很好，但在 OOD 测试集掉了多少？
```

gap 越大，说明 distribution shift 造成的性能损失越严重。TTA 方法以后要证明自己有用，通常就要看它能不能提高 OOD performance，或者缩小这个 gap。

**10. 输出文件怎么看**
结果会保存到：

```text
outputs/runs/<run-name>/config.json
outputs/results/<run-name>_raw.csv
outputs/results/<run-name>_summary.csv
```

`raw.csv` 是每个 dataset + seed 一行。比如已有的 `smoke_assistments_raw.csv` 里有：

```text
dataset=assistments
seed=0
id_balanced_accuracy=0.8888
ood_balanced_accuracy=0.6301
generalization_gap_balanced_accuracy=0.2587
```

这说明这个 smoke run 里，模型在 ID 上表现不错，但到了 OOD 明显掉性能。这正是 TableShift / OOD 实验想研究的问题。

`summary.csv` 是按 dataset 汇总多个 seed 的均值和标准差。如果你跑 3 个 seed，它会变成论文表格里常见的：

```text
mean ± std
```
